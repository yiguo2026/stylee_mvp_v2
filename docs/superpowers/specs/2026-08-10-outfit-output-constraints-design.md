# Stylee 搭配输出合理性约束设计

> 状态：已完成产品讨论，待书面复核
>
> 日期：2026-08-10
> 范围：生产推荐模型服务 `/recommend`；不修改 App 交互和现有业务响应结构

## 1. 背景

当前生产推荐链路为 B0 意图解析 → B1 候选池 → B2 范例检索 → B3 模型生成 → B4 硬校验与评分 → B5 排序和多样性 → B6 置信度。B4 已能校验真实衣橱引用、上装/下装/连体装结构、鞋数量和外套数量，但当前槽位模型不能准确表达真实叠穿，也缺少颜色复杂度、正式度跨度、场景风格池和可解释的失败重生成机制。

本设计将零散的穿搭标准收敛为可执行的三层规则，并在不改变 App 交互的前提下，让模型服务只返回通过约束的结果。

## 2. 目标与非目标

### 2.1 目标

- 服务端兜住真实性、结构完整性和核心数量约束，模型不能绕过。
- 用户明确 Query 可以覆盖场景、温度和审美类默认规则，但不能覆盖真实性与结构规则。
- 衣橱不足时允许使用明确标记的建议补齐单品，不虚构为用户已有。
- 首轮失败时根据具体违规原因定向重生成，且最多增加一次 B3 调用。
- 保持现有 `owned_item_ids`、`recommended_items`、`comment` 响应结构兼容。
- 为每条拒绝原因提供稳定错误码和服务端观测指标。

### 2.2 非目标

- 不修改 App 页面、提示、卡片标签或其他交互逻辑。
- 不改变衣橱录入、识别或数据库结构。
- 不新增视觉模型调用，不读取单品图片重新分析视觉面积。
- 不把当前无法可靠计算的视觉规则伪装成硬约束。
- 不调整 Gamma 实验路径；本设计只覆盖生产 `/recommend`。

## 3. 核心原则与优先级

规则冲突按以下顺序裁决：

1. 真实性与结构合法性。
2. 用户 Query 中的明确要求。
3. 场景着装底线与场景风格池。
4. 温度和天气默认建议。
5. 审美软规则。

“安全”和“合适”必须分开：真正的安全问题不能被 Query 覆盖；场景是否合适可以被明确 Query 覆盖；普通温度舒适度只在用户未指定时生效。Query 覆盖必须是规则级、显式的覆盖，不能因为出现模糊风格词就关闭整组保护。

## 4. 规则分层

### 4.1 绝对硬约束

绝对硬约束不可被 Query、场景或温度覆盖。任何一条违反时，该候选整套废弃。

| 错误码 | 规则 | 计算口径 |
|---|---|---|
| `H_OWNED_REF_EXISTS` | 已有单品必须真实存在 | `owned=true` 的 `ref` 必须存在于本次请求的衣橱索引 |
| `H_OWNED_REF_UNIQUE` | 同一已有单品不能重复 | 同一 `item_id` 在一套中最多出现一次 |
| `H_FEET_EXACTLY_ONE` | 鞋恰好一双 | 已有和建议单品合计，`FEET == 1` |
| `H_BAG_AT_MOST_ONE` | 包至多一个 | 已有和建议单品合计，包 `<= 1` |
| `H_HAT_AT_MOST_ONE` | 帽至多一顶 | 已有和建议单品合计，帽 `<= 1`；无法区分帽/围巾的旧数据不据此误杀 |
| `H_BODY_COVERAGE` | 上下身完整覆盖 | `上装 + 下装` 或 `连体装`，外套不能代替上装 |
| `H_DRESS_BOTTOM_EXCLUSIVE` | 连体装与普通下装互斥 | 选择连体装后不得再选择普通下装 |
| `H_UPPER_LAYER_RANGE` | 上身为一至三层 | 上身穿着层合计 `1..3`，鞋、下装和配饰不计入层数 |
| `H_OUTER_AT_MOST_ONE` | 外套至多一件 | `outer` 层最多一件，禁止两件外套同时出现 |
| `H_GAP_SOURCE_EXPLICIT` | 建议单品不能伪装为已有 | 非衣橱单品必须 `owned=false` 且提供 `gap`，不得生成虚假衣橱 ID |

### 4.2 Query 可覆盖的默认硬约束

默认硬约束在用户没有明确提出相反要求时生效。B0 只为被用户明确覆盖的具体规则生成 override。

| 错误码 | 默认规则 | 覆盖示例 |
|---|---|---|
| `D_COLOR_FAMILY_MAX` | 彩色家族不超过三种；中性色家族不超过两种 | “我要多彩撞色” |
| `D_COLORED_ITEM_MAX` | 彩色单品不超过三件 | “全身彩色叠穿” |
| `D_FLUORESCENT_MAX` | 荧光色单品至多一件 | “荧光撞色” |
| `D_FORMALITY_SPAN` | 单品正式度最大跨度不超过一级 | “西装配运动鞋” |
| `D_SCENE_STYLE_POOL` | 输出主风格属于当前场景风格池 | 明确指定池外风格 |
| `D_STYLE_CONFLICT` | 默认避开互斥风格组合 | 明确要求甜酷、法式工装等混搭 |
| `D_WEATHER_COMPAT` | 用户未指定时应用温度与天气兜底 | “不考虑天气”“室内有暖气” |

颜色按标准化颜色家族计算，不按原始字符串逐字计数。黑、白、灰、米、裸、驼、棕、藏青等归入中性色家族，但中性色不是无限免费使用。荧光规则只在颜色被可靠识别为荧光色时硬判；未知色不作为荧光色处理。

### 4.3 软评分

以下规则用于排序和生成指导，不直接废弃候选：

- 单一视觉焦点。
- 松紧平衡。
- 腰线表现。
- 材质不超过三类且质感协调。
- 7:2:1 的主色、辅助色、点缀色倾向。
- 长短层次。

当前请求没有视觉面积、图案强度、光泽、衣长和腰线可见性等可靠字段。相关事实缺失时标记为 `unknown`，不因此拒绝候选。未来补齐可靠数据后，可逐条将软规则升级为默认硬约束，而不是一次性整体升级。

## 5. 正式度与风格建模

`aesthetic_style` 和 `formality_level` 必须分开：

- `aesthetic_style` 描述静奢、法式、工装、哥特等审美语言。
- `formality_level` 描述具体单品的正式程度，使用 L1（正式）至 L4（街头/运动）。

静奢、极简、先锋、复古、哥特等风格都可能跨多个正式度，因此风格只能提供默认正式度范围，不能直接决定单品正式度。`D_FORMALITY_SPAN` 根据一套中各单品的正式度事实计算，不根据整套风格名称计算。

互斥风格表用于默认强约束，但不是永久禁配表：

- 用户未要求混搭时，互斥组合触发 `D_STYLE_CONFLICT`。
- 用户明确要求混搭时，允许一个主风格和一个辅助风格。
- 一套最多两个输出风格，且主风格必须明确。
- 风格覆盖不影响真实性、结构和数量约束。

## 6. 衣橱缺口策略

“正常最多建议一件”是偏好目标，不是绝对上限：

- 衣橱能够形成完整结构时，额外建议单品最多一件。
- 衣橱缺少必要槽位时，允许按实际缺口补齐上装、下装、鞋或天气要求的外套。
- 所有建议单品与已有单品一起参与鞋数、层数、颜色、正式度和风格校验。
- 结果排序时，在满足 Query 和有效规则的方案中优先选择已有单品占比更高的方案。
- 衣橱没有任何可用单品时，允许返回全部由建议单品组成的合法方案；外部仍使用现有 `recommended_items` 表达，不增加新的交互状态。

## 7. 内部数据结构

### 7.1 `ConstraintPolicy`

B0 在现有场景规格之外产生内部约束策略：

- 当前启用的绝对硬约束。
- 当前启用的默认硬约束。
- Query 明确覆盖的规则及其证据类型。
- 软规则权重。
- 温度是否参与兜底。

Query 原文不进入日志；trace 只记录被覆盖的规则码。

### 7.2 `ItemFacts`

B1 根据当前已有的品类、名称、颜色、材质、版型、袖长、季节和场合标签，确定性地生成：

- 核心槽位和可承担的上身层级。
- 标准化颜色家族、中性色和荧光色标记。
- 正式度及其置信度。
- 可用风格标签及其置信度。
- 材质家族和版型类别。

不得为补齐这些事实新增模型调用。事实置信度不足时设为 `unknown`，依赖该事实的默认硬规则降为软评分，不影响绝对结构校验。

### 7.3 B3 内部生成结构

B3 内部 JSON 在现有 `id/gap/role` 基础上增加：

- 上身单品的 `layer_role`：`base | mid | outer`。
- `primary_style`。
- 可选的 `secondary_style`。

这些字段只用于服务端交叉校验。模型自报的颜色、正式度和真实性不能覆盖 `ItemFacts` 或衣橱索引。适配器在返回 App 前剥离内部字段。

### 7.4 `ValidationResult`

每套候选返回：

- `valid`。
- `errors`：绝对硬约束或仍生效的默认硬约束错误码。
- `warnings`：软规则和未知事实。
- `retryable`：错误是否可通过定向重生成修复。
- `scores`：现有四维评分加软规则分。

## 8. 推荐数据流

1. B0 解析场景、用户明确要求和规则级 override。
2. B1 标准化候选单品事实，并计算必要槽位缺口。
3. B2 继续使用现有范例检索，不因本设计新增模型调用。
4. B3 首轮一次请求生成 `2 × n` 套；当前 `n=3` 时生成六套。
5. B4 对全部候选执行同一套代码校验，非法候选整套废弃，不静默修改模型选择。
6. B5 对合法候选去重、评分并保证多样性。
7. 首轮合法结果达到三套时，返回排名最高的三套。
8. 首轮只有一至两套合法结果时，直接返回合法结果，不触发重生成。
9. 首轮零套合法结果时，进入失败分类：
   - 模型违反可修复规则：携带错误码和正确约束定向重生成。
   - 必要槽位无候选：允许通过 `gap` 补齐缺失槽位后重生成。
   - 默认规则导致不可满足：仅按优先级放宽可覆盖规则后重生成。
   - 绝对结构本身不可满足：跳过盲目重试，直接进入安全保底。
10. 第二轮不重复 B0 和 B2，只运行一次 B3，生成 `n + 1` 套；当前 `n=3` 时生成四套。
11. 第二轮最多执行一次；通过 B4 后返回最多三套合法结果。
12. 第二轮仍无合法结果时，由服务端确定性保底组合器构造满足绝对硬约束的方案；默认硬约束和软规则尽力满足，但不得返回未经校验的模型候选。

## 9. 确定性保底组合器

保底组合器只在两轮均无合法模型输出，或绝对结构无法由当前候选直接满足时运行：

- 优先从真实候选池选择已有上装或连体装、下装和鞋。
- 缺少必要槽位时生成结构化 `gap`，不生成虚假 `item_id`。
- 天气规则仍生效且缺少外套时，可补一个外套 `gap`。
- 不添加非必要包、帽或其他配饰。
- 每次构造后必须重新经过同一个 B4 校验器。
- 若连绝对硬约束都无法满足，则返回空 outfits，而不是返回非法结果。

确定性保底只保证真实性与结构安全，不声称达到模型级审美质量。

## 10. 延迟控制

- 没有重生成时，新增标准化和校验代码的 p95 目标小于 50ms。
- 首轮仍是一轮 B3 调用生成六套，不增加现有模型调用次数。
- 只有首轮零套合法时才增加一次 B3 调用。
- 第二轮生成四套，不继续复用首轮六套的固定数量。
- B0、B1 和 B2 结果在重生成时复用。
- 单次推荐最多两次 B3 调用，不允许无界循环。

已有线上样本中，成功 B3 调用约 6.854 秒；因此触发重生成时预计额外增加约一次 B3 时延，通常为 7～15 秒。实际平均增量由零合法结果的触发率决定，上线后通过 trace 统计。

## 11. 对外兼容性

App 继续发送当前 `/recommend` 请求，继续接收：

```text
owned_item_ids
recommended_items
comment
```

本设计不要求修改页面、结果卡、提示语或用户操作。新增 trace 字段是向后兼容的服务端诊断信息，现有 App 可以忽略。

## 12. 观测

在现有服务 trace 中增加：

- `first_pass_valid`
- `rejected_by_rule`
- `query_overridden_rules`
- `retry_triggered`
- `retry_candidate_count`
- `retry_duration_ms`
- `recommended_gap_count`
- `fallback_type`

`rejected_by_rule` 只包含稳定错误码和计数。日志不得记录 Query 原文、衣橱内容、模型正文、用户图片或凭证。

## 13. 测试策略

### 13.1 规则单元测试

- 每条绝对硬约束覆盖合法、非法和边界案例。
- 每条默认硬约束覆盖默认生效、明确 Query 覆盖和事实未知三种情况。
- 验证建议单品与已有单品采用同一套数量和结构规则。
- 验证帽/围巾无法可靠区分时不会误触发帽数量规则。

### 13.2 Pipeline 测试

- 六套中至少三套合法：只返回前三套，不重生成。
- 六套中一至两套合法：少量返回，不重生成。
- 六套全部非法且可修复：只重跑 B3，第二轮请求四套。
- 六套全部非法且结构不可满足：不盲目调用模型，进入确定性保底。
- 第二轮仍非法：不会把非法模型候选透传给 App。
- 空衣橱、缺鞋、缺下装和冷天缺外套均能生成合法 gap。

### 13.3 契约与回归测试

- `/recommend` 请求格式保持兼容。
- App 业务响应仍只依赖 `owned_item_ids`、`recommended_items` 和 `comment`。
- 现有 B0、B2、评分、多样性和 request trace 测试继续通过。
- 模型 provider 未按内部 schema 返回时，解析失败按现有错误契约处理。

## 14. 验收标准

- 返回结果的绝对硬约束违规率为零。
- 每个已有单品都能追溯到本次请求中的真实衣橱 ID。
- 用户明确覆盖只影响对应默认规则。
- 单次推荐最多增加一次 B3 调用。
- 首轮无重生成路径新增代码耗时 p95 小于 50ms。
- 第二轮候选数固定为 `n + 1`。
- 模型服务失败时不返回未经校验的模型候选。
- App 请求和业务响应契约保持兼容。

## 15. 实施边界

后续实现应优先落在 canonical `fitzw/style-model`，再同步到本仓库的 `model-service/` 集成副本并运行同步检查。预计涉及：

- `stylee/contracts.py`
- `stylee/constraints.py`
- `stylee/scoring.py`
- `stylee/pipeline.py`
- `stylee/providers/openai_compat.py`
- 对应规则、provider 解析、pipeline 和服务测试

不修改 `src/app/`、页面组件、设计系统或 App 交互逻辑。
