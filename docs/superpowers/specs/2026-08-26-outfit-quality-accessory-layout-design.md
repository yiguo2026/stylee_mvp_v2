# Stylee 穿搭质量、配饰规格与语义布局设计

> 状态：已完成产品讨论，待书面复核
>
> 日期：2026-08-26
> 范围：生产推荐模型服务 `/recommend`、向后兼容的响应增强，以及 App 穿搭画布布局
>
> 视觉审查板：[Stylee 穿搭推荐｜模型规则 × 配饰规格 × 语义布局审查板](https://www.figma.com/design/F4ctd6L7WbcO3DJVArkk47)

## 1. 背景

当前穿搭画布已能按单品数量自适应排列、拉开上下装和裤鞋间距，并在布局后对整组做水平居中。但审查样例暴露出三个相互关联的问题：

1. 结构合法不等于穿着合理。现有 B4 允许一至三层上身穿着，但主要按 `TOP / OUTER` 品类计数，没有确定性校验 `base / mid / outer` 的层级顺序和具体单品兼容性。普通衬衫与高领毛衣等需要特殊穿法才能成立的组合可能漏过。
2. 配饰只有分散的代码缩放常量，没有正式的尺寸范围和风格进入条件。包、帽、围巾可能为了增加单品数量而同时出现。
3. 当前布局把前两个配饰放入外围位置，其余配饰放入底部通用带。结果顺序为包、帽、围巾时，围巾会靠近鞋区；通用带不理解头部、颈部、携带和足部语义。

审查截图来自手工拼装的布局 Demo，不是一次真实模型推荐。它不能证明线上模型实际返回了该组合，但准确暴露了模型约束、响应契约和 App 布局之间缺少统一语义的问题。

本设计采用端到端语义方案：模型服务负责搭配合法性和角色标注，响应通过可选字段把角色传给 App，App 只负责按语义区域完成视觉编排。前端不重复实现搭配审美，也不随机改变模型返回的 n 件结果。

## 2. 与既有设计的关系

本设计是 `2026-08-10-outfit-output-constraints-design.md` 的增量修订：

- 保留绝对硬约束 `H_UPPER_LAYER_RANGE = 1..3`，三层仍是系统能够表达的安全上限。
- 新增默认规则：普通推荐最多两层上身；只有用户明确要求三层叠穿时才允许三层。
- 修订旧设计中“`layer_role` 只在服务端使用、适配器返回前剥离”的边界。现有业务字段保持不变，但新增可选 `layout_items`，向 App 暴露经服务端校验后的布局角色。
- 不改变 B0 → B1 → B2 → B3 → B4 → B5 → B6 主链路、最多一次定向重生成、显式 gap 或确定性保底策略。
- 本次允许修改推荐结果的共享画布和映射层，但不新增推荐交互步骤，不改变用户操作流程。

若两份设计在上身默认层数、角色是否对 App 可见或响应字段范围上冲突，以本设计为准；其余约束继续沿用旧设计。

## 3. 已确认的产品决策

1. 日常推荐上身最多两层；三层只响应用户明确提出的“三层叠穿”等要求。
2. `base / mid / outer` 是位置角色，不是必须同时填满的三个推荐槽位。
3. 两件普通上装叠穿时采用保守兼容策略。属性不足或需要特殊穿法才能成立时，不冒险推荐第二件普通上装。
4. 默认配饰为零至两件，鞋不计入配饰。配饰不是必需槽位，不为凑单品数量强行添加。
5. 模型服务是搭配规则的唯一判断方；App 根据角色布局，不重新判断穿搭是否合理。
6. App 完整展示模型返回的合法 n 件，不随机抽取、不补齐、不删除。
7. 帽、围巾、包、鞋分别进入语义区域；取消底部通用配饰带，足部区域只允许鞋。
8. 所有元素排完后按整套外接范围统一缩放和平移，使视觉整体居中并保留安全边距。

## 4. 目标与非目标

### 4.1 目标

- 阻止普通衬衫与高领毛衣等缺少可靠穿法证据的冲突叠穿。
- 在不删除三层表达能力的前提下，让日常推荐稳定收敛到一至两层。
- 让包、帽、围巾等配饰只有在数量和协调性都成立时进入最终结果。
- 为每件输出单品提供稳定、可校验、向后兼容的布局角色。
- 让常规二至六件和明确要求下七至八件的合法结果都能完整展示。
- 建立配饰和鞋的可见尺寸范围、语义区域、间距、碰撞恢复和整体居中标准。
- 用真实模型结果、确定性回归样本和多宽度截图共同验收。

### 4.2 非目标

- 不新增模型调用，也不让 App 调用模型判断布局。
- 不让模型返回坐标、缩放、旋转或画布尺寸。
- 不为本次布局改造新增数据库字段或批量重处理历史衣物图片。
- 不把缺失的领型、厚度、开合方式等视觉事实伪装成已知事实。
- 不更改透明主图的单一 master 原则；仍由 `StyleeGarmentMedia` 使用 `contain` 和语义背景渲染。
- 不调整 Gamma 实验路径。

## 5. 总体架构与职责

### 5.1 模型服务

模型服务负责：

- 从衣橱权威事实和 gap 品类派生穿着槽位、层级能力、配饰种类和可用协调信号。
- 在 B3 提示中明确日常层数与配饰数量默认值。
- 在 B4 用确定性代码校验层级结构、叠穿兼容、配饰数量和配饰协调性。
- 只把通过 B4 的内部角色映射为对外 `layout_items`。
- 继续控制重生成、保底、trace 和所有业务合法性。

### 5.2 App 映射层

App 映射层负责：

- 保留 `owned_item_ids / recommended_items / comment` 的现有映射。
- 解析可选 `layout_items` 并把角色关联到已有单品或建议单品。
- 遇到旧服务或局部无效角色时降级到现有本地分类，不丢弃单品。
- 不根据画面拥挤程度修改模型返回的单品集合。

### 5.3 共享穿搭画布

`StyleeOutfitCanvas` 和纯布局策略负责：

- 按 `layout_role` 将单品放入语义区域。
- 使用统一的角色尺寸范围、间距和层叠顺序。
- 处理碰撞、换侧、缩放、重新排布和整组居中。
- 在 320、375、393、430 和 768 pt 宽度下保持完整、无裁切和可读的构图。

## 6. 上身层级规则

### 6.1 结构角色

上身角色保留：

- `base`：贴近身体或作为整套基础的上装。
- `mid`：位于基础层和外套之间的可叠穿上装。
- `outer`：外套品类。
- `dress`：连衣裙或覆盖上下身的连体装，不与普通上装和下装混穿。

允许的日常组合为：

- `base`
- `base + mid`
- `base + outer`
- `dress`
- `dress + outer`

只有用户明确要求三层叠穿时，才允许 `base + mid + outer`。不允许 `mid` 脱离 `base` 独立出现，也不允许同一层级出现两件。

### 6.2 新增规则

| 错误码 | 类型 | 规则 |
|---|---|---|
| `H_LAYER_ROLE_STRUCTURE` | 绝对硬约束 | 角色必须与权威品类一致；`base / mid / outer` 唯一；`mid` 必须依附 `base`；外套只能是 `outer` |
| `D_UPPER_LAYER_MAX_TWO` | 默认硬约束 | 普通推荐上身最多两层；只有明确的三层叠穿请求可覆盖 |
| `D_LAYER_COMPAT` | 默认硬约束 | 两件普通上装或三层组合必须通过确定性兼容矩阵；明确指定特殊穿法时可做规则级覆盖 |

`H_UPPER_LAYER_RANGE = 1..3` 继续作为不可覆盖的安全上限。因此显式三层请求只关闭 `D_UPPER_LAYER_MAX_TWO`，不能关闭 `H_LAYER_ROLE_STRUCTURE` 或四层禁令。

### 6.3 兼容事实与保守策略

不新增模型调用。B1 根据已有品类、名称、材质、版型、袖长、保暖档和标签派生：

- `garment_kind`：如 T 恤、普通衬衫、overshirt/衬衫外套、开衫、针织背心、高领打底、毛衣、卫衣、外套、连体装或 `unknown`。
- `layer_capabilities`：可承担 `base / mid / outer` 中的哪些角色。
- `closure_mode`：可敞穿、封闭式或 `unknown`。
- `thickness_band`：薄、中、厚或 `unknown`；只能由当前事实可靠派生。

默认通过示例：

- T 恤 + 开衫。
- 衬衫 + 针织背心。
- 基础上装 + 外套。
- 连衣裙 + 外套。

默认拒绝示例：

- 高领毛衣 + 普通衬衫。
- 两件都只能承担 `base` 的普通上装。
- 第二件普通上装的种类、开合或厚度不足以判断。
- 任意无法确认完整 `base + mid + outer` 顺序的三层组合。

只有明确识别为 overshirt、衬衫外套或用户明确要求敞穿等特殊穿法时，普通衬衫才可以作为高领内搭之外的 `mid`。事实未知时不降为“可能可以”继续透传；B4 拒绝整套候选，后续重生成或保底优先选择单上装或上装加外套，不在原候选中静默删减单品。

## 7. 配饰进入规则

### 7.1 数量

配饰计数包括 `bag / hat / scarf / accessory`，不包括鞋。

| 错误码 | 类型 | 规则 |
|---|---|---|
| `D_ACCESSORY_COUNT_MAX_TWO` | 默认硬约束 | 默认零至两件配饰；明确要求丰富配饰或多配饰叠搭时可覆盖 |
| `D_ACCESSORY_COHERENCE` | 默认硬约束 | 每件配饰必须与主风格、正式度、季节或明确功能至少有一项可靠正向关系，且不能与整套已知事实冲突 |

现有“包至多一个”“帽至多一顶”等绝对数量约束继续生效。没有任何配饰也属于完整合法结果；B1、B3、B4、B5 和保底逻辑都不得把配饰当成必须补齐的槽位。

### 7.2 协调性

配饰进入最终结果需满足：

- 已知风格、正式度、季节或功能中至少一项能说明它为何属于这套搭配。
- 任何已知冲突都优先于颜色相近；不能仅因同为黑、白、米等颜色就判定协调。
- 属性不足、作用牵强时省略该配饰，不用 LLM 的一句解释替代事实校验。
- 用户明确指定“戴这顶帽子”“加围巾”等单品或穿法时，可以覆盖对应默认协调规则，但不能覆盖真实性、品类和数量绝对约束。

例如，棒球帽与风衣、正装长裤、乐福鞋之间如果缺少共同风格或明确混搭请求，默认不进入结果。冷天围巾可以由保暖功能提供可靠正向关系，但仍需通过场景和正式度冲突检查。

## 8. 向后兼容响应契约

现有字段保持原样：

```json
{
  "owned_item_ids": ["item-1"],
  "recommended_items": [],
  "comment": ""
}
```

每套 outfit 新增可选字段：

```json
{
  "layout_items": [
    {
      "source": "owned",
      "item_id": "item-1",
      "layout_role": "base"
    },
    {
      "source": "recommended",
      "recommended_index": 0,
      "layout_role": "shoes"
    }
  ]
}
```

### 8.1 字段定义

- `source`：`owned | recommended`。
- `item_id`：`source=owned` 时必填，且必须存在于本套 `owned_item_ids`。
- `recommended_index`：`source=recommended` 时必填，且必须是本套 `recommended_items` 的有效下标。
- `layout_role`：`base | mid | outer | dress | bottom | shoes | bag | hat | scarf | accessory`。

### 8.2 完整性

当服务返回 `layout_items` 时：

- 每个已有和建议单品必须恰好映射一次。
- 不得映射不存在的 ID、越界下标或同一单品两次。
- `layout_role` 必须来自 B4 校验后的权威品类和层级，不直接相信 B3 自报值。
- 字段只描述语义角色，不包含坐标、缩放、旋转、z-index 或画布尺寸。

### 8.3 版本兼容和降级

- 旧 App 忽略新增字段，现有体验不受影响。
- 新 App 遇到旧服务缺少 `layout_items` 时，继续使用当前名称/品类分类器。
- 新 App 遇到单条缺失、重复、越界或未知角色时，只让该单品降级为本地分类，不丢弃商品，不改变 n。
- 有效的服务端角色优先于本地名称推断。
- 契约错误进入匿名诊断计数，不记录用户 Query、衣橱正文、图片或模型正文。

## 9. 语义布局与尺寸标准

### 9.1 区域

| 区域 | 允许角色 | 规则 |
|---|---|---|
| `core` | `base / mid / outer / dress / bottom` | 形成中央穿着轴；外套在后，基础层和中间层按穿着顺序叠放 |
| `head` | `hat` | 位于主体上侧外围，不占足部空间 |
| `neck` | `scarf` | 位于上身肩颈附近的外围，不得进入底部通用带 |
| `carry` | `bag` | 位于主体侧上方，可根据占用情况左右换侧 |
| `micro` | `accessory` | 首饰、手表、腰带等小型单品使用侧边微型区域 |
| `foot` | `shoes` | 足部专属；禁止围巾、帽、包或通用配饰进入 |

取消 `accessory-band`。布局不再按“前两个配饰 + 其余溢出项”的输入顺序分配位置，而是先按角色确定语义区域。

### 9.2 可见尺寸目标

尺寸目标以透明主图的可见轮廓为准，而不是原始 PNG 正方形边界：

| 角色 | 可见宽度占画布 | 可见高度占画布 |
|---|---:|---:|
| `bag` | 18%–22% | 18%–24% |
| `hat` | 14%–18% | 10%–15% |
| `scarf` | 14%–18% | 18%–26% |
| `accessory` | 8%–12% | 8%–12% |
| `shoes` | 20%–25% | 按原始宽高比，不拉伸 |

共享画布继续通过 `StyleeGarmentMedia` 以 `contain` 渲染，不拉伸图片。实现以角色 media frame 和 `imageScale` 控制范围，并用已验证透明 PNG fixture 的 alpha 可见边界做校准与视觉回归。历史不透明或白底图片保持兼容，使用容器范围降级；本次不批量裁切、不修改 master、不新增数据库迁移。

### 9.3 间距与层叠

- 非连体装的上装和下装可见轮廓之间保留约 2%–4% 画布高度的小间隙，避免完全粘连。
- 下装或裙装与鞋之间保留约 5%–8% 画布高度的间隙。
- 连衣裙作为一个 `dress` 主体，不人为拆出上下装间隙。
- `outer` 位于主体后层；`base / mid` 的 z-index 按穿着语义稳定排列，不按接口数组顺序决定。
- 鞋比当前早期实现略大，但不得压缩裤鞋间距或越出安全区域。

### 9.4 自适应顺序

1. 根据服务端角色建立主体穿着轴。
2. 放置鞋并满足足部专属和裤鞋间距。
3. 按 `head / neck / carry / micro` 分配实际存在的配饰，不创建占位符。
4. 发生碰撞时依次尝试同区域换侧、在各角色允许范围内缩放、整体重新排布。
5. 计算全部放置项的外接范围；对整组统一缩放和平移，使视觉中心对齐画布中心并保留安全边距。
6. 无论 n 为多少，都不因布局拥挤删除、替换或虚构商品。

常规规则预计产生二至六件结果；明确三层和丰富配饰请求可能产生七至八件。两类结果都必须走同一布局策略，区别只来自实际角色集合，不来自随机选择的 n。

## 10. 失败处理

### 10.1 模型服务

- 首轮 B3 生成时明确默认最多两层上身、最多两件配饰。
- B4 对所有候选应用本设计的新规则，非法候选整套废弃，不静默删除冲突单品后伪装成原结果。
- 首轮零套合法时，把稳定错误码传给第二轮做一次定向重生成。
- 第二轮仍失败时，确定性保底只构造 `base/dress + bottom（如需要）+ shoes + 必要 outer`；不添加包、帽、围巾或其他非必要配饰。
- 保底结果仍经过同一个 B4；无法满足绝对结构时返回空 outfits。

### 10.2 App

- `layout_items` 缺失或局部异常只触发布局降级，不触发商品删除。
- 语义区域发生冲突时重排或统一缩放，不把配饰移动到 `foot`。
- 单张图片加载失败沿用现有媒体失败表现；其他单品仍保持其角色和整体布局，不用随机替代图。
- 整体无法达到目标尺寸时优先保全所有单品和安全边距，允许在角色最小值附近进入紧凑布局；不得裁掉鞋或配饰。

## 11. Demo 与证据边界

- 原“8件合法上限”改名为“8件结构压力测试”。手工样例不得标成模型推荐结果。
- 模型结果演示必须来自通过同一 B4 校验的真实响应或固定响应 fixture，n 由响应中的合法单品集合决定。
- Demo 不调用随机数选择单品数量，不为展示某个版式而添加模型没有返回的商品。
- 真实模型截图与结构压力测试截图分开展示，避免把布局覆盖样例当作搭配质量证据。

- `layout_items_emitted`
- `layout_contract_build_error_count`

服务端继续只记录稳定错误码和数量。`layout_contract_build_error_count` 只统计服务端无法建立一一映射的响应套数；此类套装不携带不完整 `layout_items`，旧业务字段仍按现有契约返回。App 本次不新增远程遥测，只执行本地 schema 校验和安全降级；测试覆盖缺失与无效字段，不记录衣橱 ID、商品名称、图片地址或原始响应正文。

## 13. 测试策略

### 13.1 模型规则单元测试

- 日常一层、`base + mid`、`base + outer`、`dress + outer` 通过。
- 日常三层触发 `D_UPPER_LAYER_MAX_TWO`；明确三层请求仅覆盖该默认规则。
- 四层始终触发绝对硬约束。
- T 恤 + 开衫、衬衫 + 针织背心通过。
- 高领毛衣 + 普通衬衫、两件 base-only 上装、第二上装事实未知被拒绝。
- 明确 overshirt 或明确敞穿请求可覆盖对应默认兼容限制，但仍通过角色结构校验。
- 零至两件协调配饰通过；默认三件配饰、风格冲突帽子和无可靠正向关系的配饰被拒绝。
- 配饰规则不改变鞋的精确数量约束。

### 13.2 Pipeline 与契约测试

- 首轮因新规则零合法时只定向重生成一次，第二轮仍失败进入最小保底。
- 保底不添加非必要配饰。
- `owned_item_ids / recommended_items / comment` 的内容和语义保持兼容。
- `layout_items` 对每个已有与建议单品恰好映射一次，角色来自校验后的权威事实。
- 旧响应、局部无效角色、重复 ID、越界 `recommended_index` 和未知枚举均能安全降级。
- 新字段不会改变返回单品数量和次序。

### 13.3 App 布局单元测试

- `layout_role` 优先于名称分类，缺失时才使用本地推断。
- `hat / scarf / bag / accessory / shoes` 分别进入 `head / neck / carry / micro / foot`。
- `foot` 只包含鞋；不存在底部通用配饰带。
- 上下装和裤鞋可见间距处于目标范围。
- 单层、两层、连衣裙、三层显式请求、零至多配饰均保持正确 z-index。
- 二至八件合法角色集合都完整返回 placement，ID 不丢失、不重复。
- 布局完成后的外接范围在安全区域内，整组中心落在画布中心允许误差内。

### 13.4 视觉与真实结果验收

- 使用固定透明 PNG fixture 校验包、帽、围巾、鞋的 alpha 可见尺寸范围。
- 使用真实模型返回分别覆盖连衣裙、单上装、两层上装、含外套、含一件和两件配饰等结果。
- 明确三层和丰富配饰请求用于七至八件压力验证，不伪装成日常推荐。
- 在 320、375、393、430 和 768 pt 宽度检查无裁切、无鞋区配饰、整体居中和安全边距。
- 对代表结果保存真实页面截图，人工检查视觉整体性；单元测试不替代截图验收。

## 14. 验收标准

- 普通请求不会返回三层上身；只有明确三层请求可以返回通过兼容校验的三层。
- 高领毛衣 + 普通衬衫等无可靠穿法证据的组合不会进入最终结果。
- 默认配饰为零至两件，且没有配饰仍是完整合法结果。
- 棒球帽等配饰不能仅凭颜色接近通过协调校验。
- 每个最终单品都有唯一有效布局角色，或在旧服务/坏数据下被安全推断；任何情况下 n 不变。
- 围巾不进入足部附近，鞋在 `foot` 独占区域，裤鞋和上下装间距符合范围。
- 二至八件合法结果全部展示、无裁切、无重复，整套视觉居中。
- 现有 App 和旧服务均能继续工作，不要求同步强制升级。
- 模型约束、契约、布局单元测试、设计系统检查、类型检查、Web 构建和真实截图验收全部通过。
