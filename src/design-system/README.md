# Stylee Design System v3.8

This directory is the implementation source for released Stylee UI foundations and components.

## Source of truth

- `design-tokens/stylee-v3.8.tokens.json` is the canonical Tokens Studio source.
- `tokens.ts` is generated by `npm run tokens:build`; do not edit it directly.
- Run `npm run tokens:check` to verify that the JSON and TypeScript output match.
- Product components consume semantic tokens (`surface`, `text`, `border`, `action`, `status`).
- Primitive colors are only for defining semantic tokens.
- Existing values in `constants/theme.ts` remain a compatibility layer while screens migrate.

## Garment media

`StyleeGarmentMedia` is the shared semantic surface for garment imagery. It
accepts a URI or React Native image source, always renders images with
`resizeMode="contain"`, and supports overlays through `children`.

Use `neutral`, `owned`, `recommended`, or `inverse` tones instead of assigning
media background colors in consumers. The consumer continues to own aspect
ratio, radius, clipping, and all other geometry.

New or replaced garment images use a verified transparent PNG master. The
service contract requires `verified=true`, `alpha_verified=true`,
`background=transparent`, `mime=image/png`, and a PNG data URI; the App rejects
anything else and limits the data URI to 12 MiB. Service processing uses Pillow
12.3.0 with a 20 MiB encoded-input limit, a 16,000,000-pixel decoded limit, a
1600 px longest processing edge, and an 8 MiB encoded-PNG output limit.

Scene backgrounds are semantic presentation, not exported garment pixels:

- `neutral`: generic garment presentation without an ownership state;
- `owned`: wardrobe media and garments the user owns in outfit and try-on contexts;
- `recommended`: missing or proposed garments;
- `inverse`: inverse/contrast presentation where the scene requires it.

Do not infer a surface from image pixels or bake a white/colored canvas into a
new master. Existing historical white-background or opaque images remain
untouched: there is no bulk migration, background variant, or database
migration. The same semantic surfaces must continue to render those historical
assets safely. Persistence success copy is exactly `已更新为透明主图`. Manual
single-item flows may preserve an original only after explicit user choice.
Background multi-item imports keep failed originals in the retry task and never
promote them into active wardrobe, recommendation, or try-on state.

## Editorial outfit canvas

`StyleeOutfitCanvas` composes existing transparent garment masters directly in
the client. It never requests a generated composite image. The pure layout
policy in `src/lib/outfitCanvasLayout.ts` selects percentage-based positions by
garment role and item count: core garments form a central dressing axis,
outerwear sits behind it, shoes remain smaller and separate below the trousers,
and accessories use natural surrounding space only when present. Roles come
from the optional server contract, while legacy responses degrade by name.
The `head`/`neck`/`carry`/`micro`/`foot` semantic zones do not compete for
positions in response order; `foot` contains shoes only. The complete group is
fit and centered by its aggregate bounds.

For an owned `WardrobeItem`, canvas metrics resolve in this order: valid
persisted `ai_recognized_attrs.visible_bounds` overrides generated preset
bounds; a matching preset still supplies the source aspect ratio. Invalid
persisted bounds are ignored, so valid preset metrics remain usable. New or
remote items without preset metrics retain valid persisted bounds and obtain
their source aspect ratio from the image at runtime; no catalog aspect is
guessed. Source-less recommended items remain placeholders.

## Engineering rules

1. Do not add raw hex colors or one-off button/card geometry to product screens.
2. Reuse a released component before creating a new page-local equivalent.
3. New reusable APIs must include disabled/loading/pressed behavior and accessibility labels.
4. Interactive targets are at least 44 × 44 pt.
5. Validate changed screens at 320, 375, 393, 430, and 768 pt widths.
6. A component change and its consuming screen ship in the same pull request.
7. New raw colors and legacy `Colors`/`Spacing`/`Radius`/`Shadow` usage fail `npm run design-system:check`.
8. New raw font size, line height, tracking, or font family declarations in product screens also fail the guard.
9. Intentional exceptions require `// ds-exception: <reason>` and PR documentation.

## Four-level typography

All product text must use one of four semantic roles:

| Role | Specification | Use |
|---|---|---|
| `display` | 24/30, display semibold | Page titles and major empty-state titles |
| `heading` | 18/24, display medium | Sheet titles, section titles, grouped-context headings |
| `content` | 15/22, UI medium | Card titles, buttons, tabs, chips, inputs, primary values |
| `support` | 12/18, body regular | Descriptions, metadata, field labels, help and status text |

Color, alignment, and truncation may respond to context. Font family, size,
line height, weight, and tracking must stay attached to the role. The Stylee
wordmark and icon/emoji glyphs are not product typography and are the only
default exceptions.

## Choice chip density

- `StyleeChoiceChip` is the active vNext shared component for compact selection controls.
- Choice chips are for compact single- or multi-select filters, not primary navigation.
- Their default visual height is 32 pt with 12 pt horizontal padding and an 8 pt radius.
- A 44 pt minimum touch area is preserved with hit slop instead of making the visible chip 44 pt tall.
- Use the shared component for filter tags and category selectors; do not reproduce its geometry in a screen.

## Wardrobe grid density

The wardrobe home grid uses `ds.component.wardrobeGrid`. Its reference
composition is a 393 × 852 pt iPhone viewport at the default text size:

- two columns and three fully visible rows between the page controls and Tab Bar;
- 16 pt screen padding, 8 pt column gap, and 8 pt row gap;
- 44 pt header and search control, followed by a 32 pt choice-chip row;
- card media uses a 4:3 `contain` frame so full garments remain visible;
- the information area is 48 pt minimum and contains one Content line plus one
  Support line.

The header owns the add action as a trailing 44 × 44 pt touch target. Do not
place a floating add button over the grid. The six-card target applies to the
stable state without a keyboard or temporary import/confirmation banner.
Dynamic Type and shorter viewports may show fewer complete rows; accessibility
must not be sacrificed to preserve the count.

See `docs/STYLEE_WARDROBE_GRID_SPEC.md` for composition, responsive, and
acceptance rules.

Run `npm run wardrobe-density:check` after any wardrobe card, grid, header,
search, choice-chip, or Tab Bar change. Use the account-independent visual
preview documented in `docs/STYLEE_DESIGN_SYSTEM_V3_8_MIGRATION.md` for manual
multi-size review.

Before release, modify and test the canonical `style-model` repository first,
sync its governed files into `model-service/`, then run:

At 320, 375, 393, 430, and 768 pt, inspect wardrobe grid/detail, outfit result,

44 x 44 pt minimum touch targets, and historical-image compatibility. A real
service release also requires approved white and patterned samples inspected on
`neutral`, `inverse`, and `recommended`; automated guards do not replace that
visual gate.
